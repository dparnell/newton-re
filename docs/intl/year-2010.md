# The year-2010 problem and the reconstruction's fix

NewtonOS 2.1 stops working properly after **5 January 2010, 18:48:31**.
The reconstruction reproduces the bug faithfully, and by default it also
fixes it. The fix is a DEVIATION: the owner decided on it on 2026-09-30.
To run the ROM's own arithmetic instead, set
`NEWTON_ROM_2010_BUG=1` in the environment.

## What goes wrong

The machine's clock and the C++ time functions count seconds from
1 January 1904 in a 32-bit unsigned word. That lasts until February
2040. The NewtonScript functions that count in seconds are different:
they count from **1 January 1993** in a NewtonScript integer, which is 30
bits wide and signed. Examples are `TimeInSeconds` (`FTimeInSeconds`,
ROM 0x00089b64: the clock's seconds less `0xa7693a00`, made an integer),
`TimeToTimeInSeconds`, `TimeInSecondsToTime` and `SetSysAlarm`. Such an
integer holds at most 2^29 - 1 seconds after 1993. At the moment above,
`TimeInSeconds` wraps to -2^29. It has run on upwards from there ever
since: it passes 0 again in January 2027.

Going forwards, nothing is lost. Every seconds value a script makes is
the true count modulo 2^30, because NewtonScript's integer arithmetic
wraps the same way (`60 * 17700000` is -11741824 in the REP). So
differences and comparisons between two such values less than 2^29
apart still come out right. What breaks is reading a value *back* as a
date:

- `TimeInSecondsToTime(s)` is NewtonScript, `46811520 + s div 60`: the
  minutes up to 1993, plus the seconds after it.
- `DateFromSeconds` (ROM 0x0008a868) and `SetTimeHardware`/
  `SetTimeInSeconds` (ROM 0x0008a20c) add `s` to 1993.
- `SetSysAlarm` (ROM 0x0030eeec) does the same, then takes the time zone
  off.

After 2010 each of these puts a date in 1992. A new note is stamped
1992. The Setup assistant's date step sets the clock back to 1992. An
alarm always lands in the past, so it fires the moment it is set, and
`SetNextAlarm` sets it again, for ever. On the host this is what hung
`newt.Newt` and `sound.PlaySound` once the real-time clock was given
the true date (47a76c4c).

## How the community fixed it on the device

This section comes from the 40Hz pages, fetched on 2026-09-30. The
patches themselves were not examined.

- 40Hz, "Newton Year 2010 Problem"
  (https://40hz.org/Pages/newton/hacking/newton-year-2010-problem/).
  It names the affected functions (`SetSysAlarm`, `TimeInSeconds`,
  `TimeToTimeInSeconds`, `TimeInSecondsToTime`), the 1993 time base, and
  the 30-bit versus 32-bit mismatch. It also describes the two
  approaches:
  - **Fix2010** (a package by Avi Drissman) uses a *hexade* of 16 years.
    It "adjusts all functions which use minutes as a time base to always
    fall into the safe interval, taking the offset for the hexade into
    account".
  - A "more low level approach is to change the offset used by the
    seconds based functions so that the safe interval starts and ends
    later". This is Eckhart Köppen's native Patch 71J059. Its successor,
    Patch 711000, adds Paul Guyot's fix for 71J059 resetting the date to
    1 January 2008 after a reset
    (https://40hz.org/Pages/newton/patches/patch711000/).
- The exact offsets and functions those patches change are not on the
  pages. The patch packages would have to be taken apart to find them.

## The reconstruction's fix

`intl/Dates.h`'s `ClockSecondsFromScriptSeconds` reads a script's seconds
back as the second that is **within 2^29 of now** (about 17 years either
way) and congruent to the value modulo 2^30:

    now   = RealClockSeconds() - 1993          (a 32-bit word)
    delta = (s - now) as a 30-bit signed integer
    clock = 1993 + now + delta

Up to 2010 the answer is exactly what the ROM computes, for every value
within 17 years of now. After 2010 it is the right date. `TimeInSeconds`
and `TimeToTimeInSeconds` are unchanged, because their wrapped values are
consistent with each other. So stored values keep their meaning: an
alarm's `TimeInSeconds` is read back correctly whenever it is read within
17 years. Unlike a moved epoch, the fix needs no conversion of data
already on a store. Its limits:

- A seconds value more than 17 years from now reads as the wrong period.
  `test_Dates` keeps the ROM's reading of `DateFromSeconds(500000000)`
  (2008) by turning the fix off around it.
- Setting the clock more than 17 years away in one step goes through
  `TimeToTimeInSeconds`/`SetTimeInSeconds`, so it lands in the wrong
  period too.

These are the places the fix changes:

- `FTimeInSecondsToTime2010` replaces the NewtonScript
  `TimeInSecondsToTime` in the global functions. `InstallFix2010` does
  this, and `TNotebook::InitToolbox` calls it after `InitScriptGlobals`.
- `FDateFromSeconds` and `FSetTimeInSeconds` (`SetTimeHardware`) in
  `intl/Dates.cpp`.
- `FSetSysAlarm` in `newt/NewtWorld.cpp`.

Tests:

- `test_Dates`'s `TestYear2010` covers the 2026 clock: `TimeInSeconds`
  is negative, the round trip is exact, `DateFromSeconds` gives 2026,
  and with the fix off it gives 1992.
- `src/host/demo/year2010.ns` boots with the host's own clock:
  - After the Setup walk, the first note is dated this year and a new
    note is dated today.
  - The Dates day view has today's title.
  - An alarm set a minute ahead rings exactly once.
  - With `NEWTON_ROM_2010_BUG=1`, the same run shows the ROM's 1992.

## The clock itself

The host's real-time clock is the one the machine's alarms are set on
(`TURealTimeAlarm`). It holds GMT, as the device's clock chip does.
`RealClockSeconds` adds the home city's offset and daylight saving, as
the ROM's code at 0x00255578 does. So the Newton shows the time in the
city that Setup or Time Zones names, not the host's own time zone.
