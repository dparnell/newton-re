# Protocols and the protocol registry

Reverse-engineering notes for Newton's *protocol* mechanism - the
interface/implementation system behind every driver and service
(`TSerialChip`, `TStore`, `TCMService`, ...) - and the registry that hands
out implementations by name. Reconstructed in `src/protocols/` (portably:
see below) with the host test `src/protocols/tests/test_Protocols.cpp`. The
facts here come from the ROM at the addresses cited in the code and from
`tools/newton-rom/analysis/classinfo.py`, which decodes the class-info
tables; `classinfos.md` (generated by it) lists every implementation the
ROM contains.

## What a protocol is in the ROM

A protocol interface is a class derived from `TProtocol` whose methods are
*glue* generated by ProtocolGen: each method loads the instance's real
`this` (`fRealThis`, +4), its dispatch table (`fBTable`, +8) and jumps to
the slot for the method (`ldr r0,[r0,#4]; ldr r12,[r0,#8]; add pc,r12,#slot*4`,
e.g. `TSerialChip::PutByte` 0x0037b40c). The dispatch table is an array of
`B` instructions: slot 0 unused, 1 `ClassInfo`, 2 `New`, 3 `Delete`, then
the interface's methods in declaration order. An implementation describes
itself with a **`TClassInfo`** (headers/OS600/Protocols.h), a relocatable
table of self-relative offsets to its names, signature, dispatch table and
monitor entry, and `B` instructions to its `Sizeof`, alloc/free, `New` and
`Delete` code, plus version and flags. Every implementation's static
`ClassInfo()` is `sub r0,pc,#imm; mov pc,lr` pointing at its table; there
are 101 of them in the MP2100 D ROM (`classinfos.md`).

Making an instance (`TClassInfo::New`, 0x0005cfd0): allocate `Size()` bytes
(the alloc proc, or `malloc` = `NewPtr`), `MakeAt` (fill in the four
`TProtocol` words: runtime 0, real this, dispatch table, monitor 0 - there
is no constructor), call the implementation's `New()` through the class
info's branch, and tell the registry (`UpdateInstanceCount`). The
interface's `New(char*)` glue is `AllocInstanceByName` + slot 2; its
`Delete()` glue is slot 3 + `FreeInstance`.

A **monitor protocol** is an instance started as a monitor
(`TProtocol::StartMonitor`, 0x0005d57c: a `TUMonitor` whose proc is the
class info's entry and whose object is the instance). Its interface's glue
pushes the argument registers, makes a result slot and calls
`MonitorDispatchSWI(fMonitorId, selector, sp)` (the registry's glue at
0x0037c7a4; a non-zero monitor result throws `evt.ex.moncall`); the
generated entry (0x0037c99c for the registry) checks the selector, copies
the arguments back into registers and calls the method, storing its result
in the slot. Selector *n* is dispatch slot *n* + 2 (0 `New`, 1 `Delete`, 2
the first method). Every implementation gets an entry proc whether or not
it is ever a monitor; the `kci_IsMonitor` flag is 0 even for the registry.

The **signature** is a capability list: `name\0value\0` pairs ended by an
empty name (`TClassInfo::GetCapability`, 0x0005d0b0; a four-character
`long` form at 0x0005d134). `TSerialChipVoyager`'s is `v2.0`,
`TKeyboardService`'s `auto; vern=1; serv=kybd`.

## The registry

`gProtocolRegistry` (0x0c100b58) is a `TClassInfoRegistryImpl` (0x20 bytes:
`TProtocol`, `fRegistry` +0x10, `fSeed` +0x14, `fComparator` +0x18,
`fSatisfyCache` +0x1c), made by `StartupProtocolRegistry` (0x0005d4e4) at
the start of `InitialKSRVTask`, started as a monitor with a 1 KB stack and
registered with itself. Nothing else is registered at startup: each
subsystem's initialisation registers its implementations
(`InitPrintDrivers`, `InitializeStoreDecompressors`, `TCardServer::MainConstructor`,
`RegisterSoundHardwareDriver`, ... - the callers of `TClassInfo::Register`).

Entries (`SProtocolEntry`, 0x14 bytes: class info, refcon, registration
count, instance count, interface hash, implementation hash, version) live
in an `NSortedArray` ordered by (interface hash, implementation hash,
version) - `TClassInfoComparator`, 0x0005c9f0. The hash
(`HashString`, 0x0005cbdc) is rotate-7-and-xor over the characters, times
0x9E3779B9, low 16 bits; nil hashes to 0xffff. A query (`Satisfy`,
0x0005c45c) hashes its names, finds where a version of 0xffffffff would go
(`Where`) and walks *down* while the checked hashes agree and the version is
at least the one asked for (`SatisfiesHash`, 0x0005c10c), comparing names
for real (`Satisfies`, 0x0005c180) - so the newest version registered wins.
A nil name matches any. Exact (interface, implementation, version 0)
queries go through a four-entry cache of class infos, most recent first,
invalidated by every registration change. `Satisfy` with a capability
(0x0005c704) also asks `GetCapability`, without the cache.

Quirks kept: a new entry's registration count starts at 0 and `DeRegister`
removes the entry once the count is 0 after decrementing, so *n*
registrations of one class info are undone by *n* - 1 deregistrations;
`First` ignores the seed, `Next` refuses a seed other than 0 that is not
the current one; `Register` with a nil class info answers -1; the registry's
own instance is not counted (it was made before `gProtocolRegistry` was
set). Every class-info access is wrapped in `newton_try` for
`evt.ex.abt.bus` (a class info on a card that was pulled): the walk treats
an unreadable class info as not matching, `Register`/`DeRegister` answer
-1 on `evt.ex.abt`. `TClassInfo::Selector` (0x0005d0a8) returns the free
proc's address (+0x20) instead of the selector branch (+0x34) - a ROM bug,
reproduced.

The `NArray` family (`NArray`, `NSortedArray`, `NComparator`,
`NBlockComparator`, `NIterator`; `src/utility/NArray.*`, 0x00127298 and
0x0012a00c and 0x0012b704) is a second container family beside
`CDynamicArray`: chunked growth that only shrinks when a whole chunk is
free (and only if asked to), sorted insertion after equal keys, a ring of
iterators kept in step. `NArray::Init` checks the *current* element and
chunk sizes rather than its arguments.

## The portable re-expression

`src/protocols/Protocols.h` replaces the DDK's header (excluded by
`sync_ddk_headers.py`) with the same names and public interface:

* interface methods are C++ virtual functions (the DDK's own
  `VIRTUAL`/`ENDVIRTUAL`, its "hasNoProtocols" mode), overridden by the
  implementation; the ROM's dispatch table is the vtable. An instance
  therefore has a vtable pointer before its `TProtocol` part; `fBTable`
  holds the class info, `fRuntime` the address the instance was made at
  (for freeing), and a class info carries `fMakeAt` - a placement new of
  the implementation, whose default constructor does nothing else -
  answering the `TProtocol*`;
* a `TClassInfo` has a function pointer for every branch and a string
  pointer for every self-relative offset, word for word; `PROTOCOL_CLASSINFO`
  in an implementation's .cpp builds it (what ProtocolGen generated);
* the `New(char*)`/`Delete()` glue of an interface is written by hand
  (`TProtocol::GlueNew`/`GlueDelete`); a monitor interface's methods pack
  their arguments into a `ProtocolMonitorArgs` and call
  `TProtocol::MonitorCall`, and the implementation's entry
  (`TClassInfoRegistryImpl::MonitorEntry`) is a switch over the selectors;
* `Become(const TProtocol*)` (no callers in the ROM) only changes
  `ClassInfo()`'s answer, and `SetType` cannot change an instance's vtable.

`test_Protocols` boots the OS, so the registry exists as `InitialKSRVTask`
starts it, and exercises a test protocol with three implementations
through the registry: lookup by names, version and capability, `NewByName`
and calls through the interface, instance counting, enumeration with the
seed, deregistration, and the registry monitor about itself.
